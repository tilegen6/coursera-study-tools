# Automatic bridge connection

The extension uses Chrome/Edge Native Messaging for one fixed operation: connect to this application's local bridge. Start-Bridge installs a per-user host once. The existing course button then obtains and validates the current local token automatically, including after a service restart. No public pairing HTTP endpoint is added.

The host is installed under `%USERPROFILE%\.coursera-study-tools` and registered under HKCU. Node and Codex executable paths are resolved at installation. Exact allowed extension origins are calculated using Chromium's unpacked-path identity algorithm (Windows UTF-16LE path, uppercase drive letter, SHA-256 prefix). An existing manifest key, if present, is respected. No new key is added, so existing extension identity and checkpoints remain intact.

Manual and native launches share one manager. An exclusive start lock serializes launches. The bridge publishes a fresh random token atomically only after binding the loopback port. Existing state is reused only after authenticated health verification. An unrelated occupied port is an error, never a reason to kill another process. Runtime state and tokens stay in the private helper directory, outside the repository and OneDrive.

Version 1.6.1 moves the Windows default home out of LocalAppData. On this machine a normal same-user Windows process could read the old registry entry but could not see the referenced manifest created from the Codex launch context. A probe under the user profile was visible. Installation preserves the previous allowed origins; startup shuts down a legacy helper only after authenticating its exact instance and build. Old installation files remain available for rollback. `tests/windows-visible-install.cjs` launches a separate same-user Windows process through WMI and checks visibility of the actual registered manifest and wrapper, rather than inheriting the installer's process context.

The native host checks its caller origin and accepts only a bounded framed JSON connect request. It cannot execute paths or commands supplied by a page. It returns a token only over the native channel to the trusted extension worker. The worker verifies health before storing it; content scripts receive status only. HTTP Host, Origin, bearer authentication and request limits stay enabled. Failed write requests are never retried after ambiguous network errors.

Alternatives considered: an unauthenticated HTTP pairing route would weaken local authentication; a token file inside the unpacked extension would place secrets in source/OneDrive and would depend on browser file caching. Native Messaging avoids both. The one-time local host registration and extension permission update are the setup cost.

Verification covers protocol framing/origin/operation rejection, concurrent launches, stale state, foreign occupied ports, restart/token rotation, bridge survival after host exit, exact extension identity, Windows paths with spaces/Unicode, and a real unpacked Chromium extension starting a synthetic course with no stored token or copy/paste.

Managed state and health include a runtime build hash. Updating the helper replaces its own authenticated instance rather than silently reusing old code. On Windows a short PowerShell Start-Process bootstrap creates the hidden service independently; it avoids inherited browser pipe handles observed with the installed Node/libuv version. The browser test closes Chromium and then verifies that the same service instance is still healthy.

Protocol reference: [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging). Identity reference: [Chromium id_util.cc](https://chromium.googlesource.com/chromium/src/+/main/components/crx_file/id_util.cc).

Since 1.4.2, creating or recovering a course session does not require a model connection. Native startup is lazy at the first solver task; an explicit connect-only recovery still verifies native startup. The solver checks authenticated health and the requesting document before its single job POST, so a stopped helper can restart safely without retrying an ambiguous POST or creating a job after Stop. Native-channel and pre-job connection failures carry a bounded BRIDGE_UNAVAILABLE code through the trusted worker/content IPC. The runner queues that unsubmitted task as blocked_dependency and continues available materials. Its existing 1/2/5/10/30-minute backoff automatically retries after connection repair; a queued failure never counts as course completion. Other execution/validation errors retain their existing handling. tests/offline-browser.cjs verifies both the missing-host path and a later single successful submission without a second user action; tests/installed-native.cjs separately verifies the real default installed host in a disposable browser profile without touching the user's Chrome profile.

Version 1.4.1 also handles updated files with a stale loaded unpacked manifest. Only an explicit course/connect click may store a short-lived private recovery intent and call runtime.reload. All extension course/model/material runs must be idle. The new worker consumes that intent once, checks the original document and profile before and after native startup, scopes operations to Chrome documentId, and validates again at the content action. Stop cancels the pending authority. No page reload, permission auto-approval, profile-store access, ID change, or automatic enrollment of an unknown extension origin is used. Chrome retains control of permission/developer-mode requirements.
